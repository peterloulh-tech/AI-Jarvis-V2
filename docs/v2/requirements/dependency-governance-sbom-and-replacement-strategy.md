## 1. 适用边界与统一准入门

本策略供未来 V2 仓库使用，不创建 V2 仓库、不修改或升级 V1 依赖。依赖包括运行时库、构建工具、传递依赖、vendor 源码、补丁、安装器组件、系统/驱动运行库和模型文件；仅出现在构建机上的工具也必须登记，但可用作用域与最终产品组件区分。

每次新增、升级、换源、改量化或改变构建选项都必须依次通过：`申请 -> 锁定 -> 来源校验 -> 许可/漏洞评审 -> 构建验证 -> SBOM/随包材料核对 -> 批准`。任一步为`阻塞`时不得进入发布基线。审批记录至少包含下表字段：

| 字段 | 最低要求 |
|---|---|
| `DEP-ID` / 生态 / 用途 / 作用域 | 稳定 ID；标明 build、runtime、installer、model 或 test |
| 名称 / 版本或 revision / 依赖关系 | 禁止仅用分支、`latest`、范围版本或可变下载地址 |
| 官方来源 / 制品路径 / SHA-256 | 源码与二进制分别记录；本地重打包须另记产物哈希 |
| 许可证表达式 / 原始证据 / NOTICE | SPDX 表达式优先；链接、固定 revision 和本地随包材料必须可回放 |
| 漏洞扫描 / 可达性 / 修复或缓解 | 记录工具、数据库时间、标识、结论和证据，不得只记“无风险” |
| 责任人 / 评审日期 / 决定 / 例外到期 | 决定只允许批准、阻塞、替换、移除；例外必须有到期日和批准人 |

## 2. 五类生态的锁定与可审计清单

| 生态 | 声明与锁定 | 来源和完整性 | SBOM/发布证据 | 直接阻断条件 |
|---|---|---|---|---|
| C/C++ | 固定 CMake、编译器、Windows SDK；vendor 固定提交、归档及子树；外部库固定精确版本 | 官方仓库或发行页、revision、源码/归档 SHA-256；构建参数与链接目标留档 | 源码组件、实际链接库、编译工具链及最终 DLL/静态链接关系 | 浮动 revision、来源或哈希缺失、无法确定实际链接内容 |
| Python | `pyproject.toml` 只作声明；为每个平台锁定全部传递版本、wheel 文件名、marker 与哈希 | 仅允许已核验索引/官方发行物；构建时等价启用 `--require-hashes`；sdist 须单独审查和复现 | Python/CPython、全部 wheels、PyInstaller 与 bootloader、捆绑模块清单 | 范围依赖直接发布、无锁/无哈希、构建时临时联网解析 |
| Node | 固定 Node、包管理器和 lockfile 版本；所有节点有精确版本 | 每个传递节点必须有 registry/source 与 integrity；Git 依赖固定提交并另存 SHA-256 | 全依赖图及实际打包的 Electron、Chromium、Node、native addon notices | lock 与 manifest 不一致、来源/integrity 缺失、install script 未评审 |
| 安装器/二进制 | 固定 Electron Builder、NSIS、PyInstaller、VC runtime、CUDA 等版本与构建来源 | 固定官方下载位置、EULA/Redist 版本、签名前后文件 SHA-256 | 对最终 staging 目录和安装包生成文件清单、组件 SBOM、许可证集合与签名记录 | 只登记构建脚本而未扫描最终包；不可追溯 DLL 或无再分发依据 |
| 模型/运行时 | 固定仓库 commit、文件路径、字节数、SHA-256、量化/转换工具和 runtime 兼容版本 | 保存固定模型卡、许可证/NOTICE、上游与量化来源；禁止可变 URL | 模型包独立 SBOM；每个权重为组件或制品，关联 runtime 与原模型谱系 | 权重哈希、许可、来源、修改说明或 runtime 兼容关系任一缺失 |

锁文件和 SBOM 都必须从干净环境重算并纳入评审；前者保证解析输入可复现，后者描述实际交付内容，两者不能互相替代。平台条件、可选组和 CPU/CUDA 变体须分别生成依赖图，不得用一个开发机清单代表全部发行组合。

## 3. SBOM 格式与模板

正式产物统一使用 **CycloneDX 1.6 JSON**。程序包和模型包分别生成 SBOM，发布时再以顶层产品 BOM 引用对应子 BOM；源码审计可保留额外清单，但不得替代 CycloneDX。每份 BOM 必须可通过 1.6 schema 校验，并满足以下字段模板：

| 对象 | 必填内容 |
|---|---|
| `metadata` | UTC `timestamp`、生成工具及版本、顶层 `component`、产品版本、Git commit、构建/发布 ID |
| `components[]` | 唯一 `bom-ref`、`type`、name、精确 version/revision、scope、purl（适用时）、SHA-256、许可证表达式或 `NOASSERTION` |
| 来源与证据 | `externalReferences` 指向固定源码/发行页；properties 记录制品路径、来源类型、许可/NOTICE 证据路径 |
| 关系与谱系 | `dependencies[]` 完整表达直接/转移关系；vendor、patch、重打包、量化模型用 `pedigree` 或 properties 记录 ancestor 与修改 |
| 安全状态 | vulnerability ID、来源、评级、分析状态、可达性、缓解/修复版本和评审时间；没有扫描证据不得写未受影响 |

单项组件审计模板如下；生成器可以扩展字段，但不得删除这些列对应的信息：

| DEP-ID | bom-ref | 生态/作用域 | 名称 | 版本/revision | 来源 URL | 制品/路径 | SHA-256 | license/notice 证据 | 上游/patch/量化谱系 | 漏洞结论 | 决定 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 示例占位 | 生成时填写 | 生成时填写 | 生成时填写 | 精确值 | 固定来源 | 实际交付项 | 64 位小写十六进制 | SPDX + 证据路径 | 无则写不适用 | 扫描批次 + 状态 | 批准/阻塞/替换/移除 |

发布证据包还必须保存：锁文件、依赖准入记录、SBOM schema 校验结果、漏洞扫描输入/数据库时间、许可证/NOTICE 汇总、最终文件哈希清单和例外清单。SBOM 中出现 `NOASSERTION`、无法解析的组件或最终文件清单未覆盖的二进制时，发布门失败。

## 4. Vendor 与 patch 规则

每个 vendor 根必须有机器可读清单，至少记录：上游名称/URL、固定 revision、归档 SHA-256、导入后子树哈希、导入工具及命令、排除项、许可证/NOTICE 路径和复核日期。禁止手工修改 vendor 树后不留痕，禁止把模型或媒体权利归入源码许可证。

所有本地改动只进入 `patches/`，并由有序清单确定应用顺序。每个 patch 必须记录 patch ID、适用上游 revision、patch 文件 SHA-256、作者/日期、理由、修改边界、许可影响、验证方法及上游提交/拒绝状态。干净上游获取、哈希校验、按序应用和结果树哈希必须可复现；冲突、模糊应用或结果树不一致均阻断。

出现以下任一变化即重新走准入：上游 revision、归档来源、patch 内容/顺序、编译开关、静态/动态链接方式、嵌入资产、许可证文件或最终二进制依赖图变化。安全修复也不得绕过来源、许可和回归验证。

## 5. 许可证与漏洞阻断规则

| 门 ID | 阻断条件 | 解除要求 |
|---|---|---|
| GOV-LIC-01 | 许可证、版权/声音/媒体权来源未知，或只有清单字段而无原始证据 | 取得固定原始证据和适用用途确认，或移除/替换组件 |
| GOV-LIC-02 | 许可证义务与闭源商业离线分发方式冲突，包括无法履行的源码、署名、NOTICE、专利或商标条件 | 法务/许可评审确认兼容且交付物可履约，否则替换；不得以例外默认放行 |
| GOV-LIC-03 | 最终包缺少适用 LICENSE/NOTICE、修改标记、归属或 EULA/Redist 记录 | 在最终 staging 目录和安装后可访问位置验证材料完整 |
| GOV-SEC-01 | 存在可达的 Critical 漏洞，或已知被利用且没有经验证缓解 | 升级、补丁、隔离或替换后重扫并验证 |
| GOV-SEC-02 | High 漏洞无修复/缓解计划，组件已停止维护，或扫描/SBOM 因来源不明而无法完成 | 指定责任人、验证缓解和到期日；发布前未关闭则替换或移除 |

风险评级须保留扫描器原始严重度，同时结合是否进入最终包、运行时可达性、权限和攻击面形成处置结论。任何临时例外必须限定组件、版本、产品版本和到期日，附批准人、缓解措施与回归证据；例外不得覆盖许可证权利不明或无法履约。

## 6. 高风险依赖替换原则

替换优先级依次为：移除未使用能力；使用标准库/系统已批准能力；采用许可证兼容、来源稳定、维护活跃且离线可获得的同类组件；最后才允许隔离并维护最小补丁。不得因替换引入冻结范围外功能。

候选比较必须同时覆盖：冻结需求适配、Windows 11/NVIDIA 与完整离线能力、许可证/NOTICE、固定制品和哈希、维护与漏洞历史、传递依赖规模、可替换接口、包体/资源影响以及验证成本。替换完成需在同一变更中更新锁文件、vendor/patch 清单、SBOM、许可证材料、风险项和受影响测试证据；旧组件及残留二进制须从最终包清除。
