## 3. O01～O09 P0 专项执行矩阵

以下步骤是在任务 9 对应行之后执行的最小专项增量；“通用期望结果”不再复述。任一逐次冻结规则失败即为该 ID `失败`，不得以其他轮次或平均值覆盖。

| ID | 专项步骤 | 必须留下的证据 | P0 判定增量 |
|---|---|---|---|
| O01 | 启动 O 后枚举模型/权重、持续会话和文字生成流；依次经历空闲、生成、待生成、生成失败和停止 | 各阶段实例 ID、PID、会话 ID、生成流 ID 与停止后资源快照 | 全程只有一个所选模型实例、一个持续会话和一个文字生成流；停止后本次模型资源清理 |
| O02 | 用 O-IN-01 触发一次长生成；在生成期间持续注入带时间标记的新画面和已启用音频，完成后再触发下一轮；再复用 BENCH-005 对同一片段执行 15/20/30 秒短时上下文对比 | 生成窗口内输入接收序列、上下文更新时间、后续结果所引用的新标记、摘要所在结构化响应、模型调用数及三组数据 | 生成不切断输入或上下文；摘要随正常响应产生且不增加模型调用，内部上下文参数不向用户开放；15/20/30 秒仅形成对比数据，不改变当前默认目标或冻结规则 |
| O03 | 智能沉默关闭；先用 O-IN-01 取得自主触发，再用平静片段跨过低/标准/高的 12/8/6 秒系统节奏 | `trigger_source`、触发时点、同一会话 ID、模型/系统触发接口与额外检测调用清单 | 自主与系统节奏两类路径均可区分且共用会话；无帧差、音量突变或句末触发壳。候选不支持时如实记失败/阻塞并关联 O10，不改规则 |
| O04 | 智能沉默开启；运行 O-IN-02，再分别注入进程退出、硬超时、连续完整失败和输入流显式错误中的适用信号；对可选音频执行单路及全部失效 | 系统节奏调用数、自主输出/沉默、故障信号、动作、剩余输入集合、设备切换/重连和模型调用清单 | 系统节奏强制输出为 0；长时间无弹幕不算故障；显式故障仍按冻结路径处理；单路音频失效使用剩余输入，全部失效退化为纯画面；无自动切设备、无限重连或独立健康看门狗/探测调用 |
| O05 | 对低/标准/高及自定义档分别执行多轮；风格列表按 1、2、4+ 分组，并插入一轮结构化失败 | 每轮单次调用、三个批次的风格顺序、人格/语言快照、轮询前后索引 | 每轮仍是当前轮到的三个风格批次；不足三个风格循环补足，4+ 风格跨轮覆盖；失败不回滚；不因更多风格增批或补调用 |
| O06 | 内置低/标准/高分别核对每批条数和 12/8/6 秒系统节奏；自定义依次用 1、225、226、350、351、500 字预算，并验证 >500 无法开始 | 档位、每批目标/实际条数、轮次总条数、节奏、预算组和生效硬超时配置 | 低/标准/高每批分别 1～2、2～3、3～5 条，每轮三批形成 3～6、6～9、9～15 条；内置硬超时均为 12 秒；自定义 1～225/226～350/351～500 字严格对应 12/16/20 秒；不得改写或外推 |
| O07 | 占用唯一生成流；依次验证“系统→更新系统”“系统→自主”“自主→系统”“自主→更新自主”，随后释放生成流 | 每次槽写入/覆盖/忽略/领取记录、触发来源、槽深度峰值、生成流数 | 待生成槽峰值为 1；自主优先，同类保留较新内容；无历史生成请求队列，系统触发不能覆盖待处理自主触发 |
| O08 | 顺序注入 O-IN-05 的有效、部分无效、超量、全空变体；每个变体观察本轮结束至下一正常触发 | 逐批校验/截断/丢弃、有效发送、完整失败、额外模型调用及立即重试计数 | 有效批独立发送并服从档位上限；坏批独立丢弃；只有整轮无有效弹幕计完整失败；补调用和立即重试均为 0 |
| O09 | 先注入连续 3 次完整失败；再注入会话重建失败；分别让内置档及 1～225、226～350、351～500 字组越过适用硬超时；最后在 10 分钟滚动窗口制造第 1、2、3 次及超额进程重启 | 失败计数、会话重建、代次、进程 PID、适用硬超时、首片段/完整结果时间、重启等待、保护状态、旧结果与孤儿计数 | 第 3 次完整失败重建会话；重建失败或硬超时重启进程；中途输出不延长时限；窗口内第 1/2/3 次重启分别立即/等待 5/15 秒，超额进入保护；旧代次生效和停止后孤儿均为 0，UI 始终可停止 |

O09 的信号—动作—残留必须同时填写任务 4 的故障记录；硬超时完成时延、恢复耗时和资源数据仍填写任务 3 模板。禁止在本文件添加新的连续失败次数、重启次数、恢复时限或探测机制。

## 4. O10 P1/选型门槛证据

O10 不以“规划存在”判通过。每个候选模型都必须在 Windows 11 64 位、NVIDIA 16GB 显存且主要供模型使用的独占环境，关闭 TTS，执行 O-IN-07；若候选不支持自主触发或组合能力，仍提交原始失败/阻塞证据，不得由外部业务触发壳、额外模型调用或 TTS 替代。

### 4.1 执行顺序

1. 锁定候选模型、量化、运行时、应用提交、硬件/驱动、配置与 O-IN-07 哈希；枚举加载前资源。
2. 启动 O 并证明一个模型实例、一个持续会话、一个文字生成流；记录加载、稳态、生成峰值和停止后资源。
3. 在同一会话连续送入音画，在一次生成前、生成中和生成后保留输入接收标记；不得因文字生成停止采集。
4. 由候选模型原生或经评审的等效能力产生自主触发，输出三个可校验的结构化文字批次；记录接口、触发来源和完整原始响应，TTS 调用数必须为 0。
5. 复用 BENCH-001～005 记录低/标准/高、自定义预算、忙碌单槽和短时上下文数据；需要稳定性证据时复用 BENCH-019，不另建场景或阈值。
6. 停止并记录显存、PID、孤儿和结果；按四态给出候选限制，不把模型独占数据外推为高负载游戏同机能力。

### 4.2 证据完整性与 16GB 独占字段

以下字段直接写入任务 3 的 `performance-record-templates.md` 及既有 CSV/资源趋势记录；本表只是 O10 完整性检查，不是新模板。

| 证据组 | 必填字段/证据 | 完整性判定 |
|---|---|---|
| 候选身份 | model、model_version、quantization、runtime、runtime_version、应用提交/构建、配置哈希 | 任一缺失则 `阻塞` |
| 16GB 独占环境 | Windows/驱动、GPU/显存、CPU/RAM、电源策略、其他 GPU 进程清单、模型进程归属 | 必须证明“主要供模型使用”；不得写成综合游戏承诺 |
