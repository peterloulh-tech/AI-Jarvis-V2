> 使用规则：本文是待执行方案。实际结果、证据、构建与环境未填写时，任何 case 均不得预判通过。

## 1. 执行头与共同前置

每次执行至少记录：`execution_id`、case ID、Windows 11 版本/Build、NVIDIA GPU/驱动、应用提交、程序/运行时/模型清单与摘要、网络阻断方式、用户配置 fixture、证据根引用和执行/复核人。兼容性结论必须记录前后活动版本身份元组。

共同规则：

- 使用干净的正式支持 Windows 11 64 位物理机；是否预装 Python、Node.js、开发工具必须实测记录。
- 离线 case 在把受检包复制到目标机后、执行安装前切断外部网络；本机 IPC 单独归类。
- O/V 核心闭环沿用后续功能验收定义；本文只要求入口、输入、推理/结构化结果、文字显示和停止均有证据，不重写 O/V 业务规则。
- 进程清理使用任务 4 的 PID/角色和 `MET-S06` 口径；网络/落盘/诊断隐私使用任务 6 的验证方案。
- 安装/更新/卸载耗时和包体积只记录，不设置未经实测的门槛。

## 2. 安装与断网步骤

### INSTALL-TEST-001：无需开发环境的全新安装

1. 记录 Python、Node.js、编译器、包管理器和开发环境未预装的证据。
2. 使用受检程序安装包完成安装，不临时安装开发依赖。
3. 启动应用并确认配置页可交互，记录 `MET-C01/C07`、程序/运行时身份和错误。
4. 检查用户可见安装、错误和完成文案是否符合任务 5 简体中文边界。

通过：安装和首次启动成功；未安装或调用外部开发环境；身份字段完整。任何缺失依赖导致的手工开发环境补装均为失败。

### INSTALL-TEST-002：完整离线包安装

1. 在联网准备机核对完整离线包清单，确认程序、运行时和声明模型均在本地包内。
2. 把包复制到目标机，记录包大小和摘要后切断外部网络并清空/隔离 DNS 路径。
3. 在断网状态完成安装和首次启动；监控 DNS、外部连接、模型下载事件和本机 IPC。
4. 分别执行 OFFLINE-TEST-001/002。

通过：安装和核心闭环不访问外部网络，不在线补齐模型；DNS、外部连接和在线模型下载均为 0；包体积记录为 `CAL-030` 实测数据而非承诺。

### OFFLINE-TEST-001/002：O/V 核心离线闭环

对 O 和 V 分组执行：确认不登录 → 进入配置页 → 选择已安装模型和本地输入 → 开始 → 获得可观察结构化结果与文字显示 → 暂停/恢复（适用时）→ 停止并清理。全程保持外网阻断，记录 `MET-C04`、网络计数、活动身份和任务 4 清理证据。

通过：两种模式各自闭环完成；未声明外连、DNS、账号/登录和在线模型下载均为 0；停止结果满足既有规则。

## 3. 程序与模型更新

### UPDATE-PROGRAM-001：程序小版本成功更新

1. 建立旧程序 + 现有模型 + 已知稳定用户配置的可运行基线，保存各清单摘要和配置 fixture 摘要。
2. 在停止状态由用户选择本地程序包，执行 precheck → stage → verify → activate → postcheck → cleanup。
3. 对照程序、模型、运行时、配置和日志 schema 的前后身份；执行一次离线核心冒烟。
4. 搜索更新期间模型下载/重写证据和自动外连。

通过：程序身份变更为目标版本；全部现有模型摘要保持不变且无模型下载；兼容配置保持；离线冒烟通过；记录阶段和身份完整。

### UPDATE-PROGRAM-002：程序更新失败保护

分别使用受控摘要不匹配、兼容不通过和激活/postcheck 失败样本；每个样本从同一可运行基线独立执行。记录失败阶段、错误码、回退结果、暂存残留和最终活动身份，再用变更前版本完成离线核心冒烟。

通过：失败候选未成为已知可运行版本；变更前程序/模型/配置组合保持或恢复；原版本核心冒烟通过；暂存残留按规则清理。不得以“重新下载安装”作为失败保护证据。

### UPDATE-MODEL-001：模型包成功替换

1. 记录当前程序、运行时和旧模型身份。
2. 用户选择本地兼容模型包，完成摘要、兼容、激活和加载检查。
3. 执行适用 O 或 V 离线核心冒烟并核对程序身份。

通过：仅目标模型身份变化；程序包不重装且身份不变；新模型验证后可用；无自动外连。

### UPDATE-MODEL-002：模型替换失败保护

分别使用摘要不匹配、兼容为 incompatible/unknown 和加载 postcheck 失败样本。通过：新模型未保持为活动项；旧模型仍可加载并完成原离线冒烟；程序身份不变；失败阶段和清理证据完整。

### COMPAT-TEST-001/002：兼容规则与未知状态

- `COMPAT-TEST-001`：选择清单声明相容的程序/模型组合，核对判定输入、结果和激活身份一致。
- `COMPAT-TEST-002`：选择 incompatible、unknown、缺清单和未知 schema 四组，确认全部在激活前阻断。

不得用实际运行崩溃作为唯一兼容检查。未知与不兼容必须同样阻断，但错误码应能区分。

## 4. 无自动联网与手动触发

### NETWORK-TEST-001：静默窗口

在已安装且配置完成的目标机，分别观察冷启动到配置页、配置页空闲、停止状态空闲和关闭后的固定记录窗口。记录进程、DNS、连接、端点类别和触发源。

通过：自动版本检查、后台版本服务、自动模型下载、遥测和上传事件均为 0；本机 IPC 单列，不伪装外连。

### NETWORK-TEST-002：用户主动获取/更新窗口

若后续构建提供用户主动联网获取包的入口，记录 UI 操作、目标来源、开始/取消时点和网络活动边界。取消后观察进程和连接，确认不转入后台继续下载或自动激活。若构建只有本地包路径，本 case 标记有依据的 `NOT_APPLICABLE`，不得虚构在线功能。

## 5. 卸载与配置选择

### UNINSTALL-TEST-001：默认保留个人配置

1. 建立可识别但不含真实敏感信息的用户配置 fixture，并启动/停止一次 O 或 V。
2. 打开卸载界面，不更改默认选择，记录默认是否为“保留个人配置”。
3. 完成卸载，枚举模型、采集、Overlay 进程和配置 fixture。

通过：界面明确选择且默认不删除；个人配置仍存在并与 fixture 摘要一致；相关残留进程总数为 0；用户可见文案符合任务 5。

### UNINSTALL-TEST-002：明确删除个人配置

重复建立相同 fixture，明确选择删除个人配置并完成卸载。通过：选择动作有证据；适用配置被删除；相关残留进程总数为 0。模型文件处理只按已评审安装说明记录，不把配置选择扩展解释为模型删除授权。

## 6. 版本化日志、诊断与主页面提示

### OBS-TEST-001：日志身份与更新阶段

执行一次程序成功更新、一次程序失败回退、一次模型替换和一次卸载。逐条核对 `update-observability-fields.md` 的通用身份、阶段、兼容、保留、回退、网络、清理和 outcome 字段。

通过：适用必填字段缺失数为 0；同一 operation_id 的前后身份和实际版本一致；未登记/禁止字段命中为 0；日志有界证据引用完整。

### OBS-TEST-002：诊断包版本一致性

停止状态手动导出默认诊断包，核对 DIAG-001 与 OBS-ID-005～012 的适用字段，并与活动版本身份及日志 schema 对照。另按任务 6 执行默认/勾选弹幕文字两组隐私检查。

通过：版本字段完整且一致；默认无原始音画和弹幕文字；无程序/模型文件或自动上传；`MP-24` 记录诊断包自身版本和 section。

### OBS-TEST-003：主页面性能提示且不自动降级

使用后续已评审的可控硬件/性能提示条件，记录提示原因、指标/校准引用、显示时点和提示前后配置快照。若尚无冻结或已校准触发条件，只检查字段/文案设计并标记 `DATA_INCOMPLETE`，不得自行写死阈值。

通过：提示在主程序页面可见、来源可追踪；模式、模型质量、频率和采集配置的自动变更次数为 0；后续用户手动修改有独立操作证据。

## 8. 完成门槛与报告边界

- 每个必测 case 必须有构建、环境、包身份、步骤、实际结果和证据；缺一项为 `DATA_INCOMPLETE`。
- 任一自动更新、后台下载、强制更新、自动版本服务、失败破坏旧版本、默认删除个人配置或卸载后残留进程均为 `FAIL_FROZEN`。
- 兼容规则或冻结资料未明确的模型卸载策略进入 `REVIEW_REQUIRED`，不由本任务补造功能。
- 本文交付不代表上述 case 已执行；真正结论由后续指定构建的记录与评审产生。
