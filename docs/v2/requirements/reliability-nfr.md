本文件把冻结的可靠性行为转成可验证的结果约束，不增加运行状态、健康探测调用或模型副本。时间点、恢复时间、资源趋势和稳定性统计均复用 AIJARVISV2-2 的 `TERM-*`、`MET-*` 与 `MP-*`；任务3继续负责性能、资源和端到端时效测量，本任务只判定故障行为、隔离、恢复、清理和长稳结果。

## 1. 判定规则与边界

| 结果标记 | 使用条件 |
|---|---|
| `PASS_FROZEN` | 冻结结果逐次满足；任何一次硬要求失败都不得被平均值掩盖 |
| `FAIL_FROZEN` | 主程序失去响应、故障扩散、旧代次结果生效、停止清理失败、出现孤儿或第二实例等任一硬要求失败 |
| `DATA_COMPLETE_PENDING_CALIBRATION` | 恢复耗时、资源斜率或保护阈值记录完整，但最终数值门槛尚未冻结 |
| `DATA_INCOMPLETE` | 缺少故障信号、动作、代次、PID、清理或证据链，无法判定 |
| `REVIEW_REQUIRED` | 冻结规则冲突、未登记故障类型或需要新增门槛；只记录并评审，不在本任务改值 |

统一约束如下：

1. 只使用冻结需求已有的显式故障信号：进程退出、O 生成硬超时、连续完整输出失败、输入流显式错误、V 任务失败/进程退出、采集失效和 Overlay 异常；不增加健康模型调用、周期性推理探测或新业务状态。
2. 每个故障记录 `run_id`、`run_generation`、组件、信号、期望动作、实际动作、故障前后 PID/代次、残留和证据。恢复后使用新代次；旧代次结果不得进入校验、队列或显示。
3. 所有等待、队列、缓冲、历史和日志必须有配置上限或保留边界，并有触顶后的覆盖、淘汰、拒绝或停止规则；具体安全上限继续待实测/后续协议任务确定。
4. `MET-T11/T12` 只按故障类型报告 N、min、max、P50、P95 和失败率，不在本任务填写最终停止或恢复耗时门槛。
5. `MET-R04/R05/R09` 记录时序和分段趋势；“不得持续无上限增长”是冻结结果边界，但 MiB/h、句柄/h 或其他最终斜率门槛保持待实测。
6. 4 小时正式窗口与主程序崩溃数 0 是冻结硬要求；8 小时固定输入/回放只属于内部工程目标，不形成对外承诺。

## 3. 故障不扩散与有界等待契约

每个组件必须有明确所有者、取消路径和终止证据。主程序不得在 UI 线程同步等待模型、采集或 Overlay 无限完成；跨组件等待必须能被暂停、停止或退出打断。任务4不规定新的毫秒级超时，而是要求执行记录填写所用配置、等待对象、退出原因和证据。

以下结果属于硬判定：暂停/停止后的新增工作数为 0；旧 `run_generation` 结果生效数为 0；停止和异常退出清理后的本次孤儿进程数为 0；第二应用实例与第二模型副本新增数为 0。队列、缓冲、历史、日志和重启记录必须有界；具体容量、保留期和 V 保护阈值仍由后续实现/实测任务评审。

## 4. 与任务3的边界

- 任务3定义性能场景、资源采样、端到端阶段和 P50/P95 汇总；任务4不修改 `performance-*` 文件或两个既有性能 CSV。
- 任务4在故障、恢复、暂停、停止和长稳场景中引用任务3的 `performance-sample-record.csv` 与 `resource-trend-record.csv` 作为原始性能/资源证据，不建立第二套资源口径。
- 任务4只判定可靠性结果：是否响应、是否隔离、动作是否符合冻结规则、旧代次是否失效、结构是否有界、是否完成清理、是否存在孤儿/第二实例，以及 4h/8h 窗口结论。
- 恢复耗时、停止耗时、显存/内存/句柄增长和性能门槛继续标记 `DATA_COMPLETE_PENDING_CALIBRATION` 或 `REVIEW_REQUIRED`。

## 5. 对外承诺边界

可引用的冻结结果仅包括：4 小时正式稳定性窗口、窗口内主程序崩溃数 0、故障不拖死主程序、停止后释放模型资源并清理相关子进程、单实例以及既有 O/V 故障行为。

在最终实现、Windows 真机和故障注入证据评审完成前，不得承诺具体恢复时间、停止时间、V 硬超时、V 连续重启保护次数、资源峰值、资源增长斜率或 8 小时对外稳定性。
